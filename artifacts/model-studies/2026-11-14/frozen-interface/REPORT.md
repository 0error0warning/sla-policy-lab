# 冻结决策接口与身体规则诊断

2026-11-14。主结果为 **v2 的完整 48 次调用**；中途停止的 v1 共 21 条记录单独保留。这里的“完整”指预定调用齐全，不代表模型都完成了答案。

**简化的已知风险选择已经能做好；身体规则计算仍不可靠。本轮没有足够证据支持把在线个体学习整体升级到 9B。thinking 的完成问题仍未解决，不能把它的未完成当作算错，更不能据此宣布模型的推理能力上限。**

## 主结果与原问题

最简的风险表只要求选择动作时，4B 和 9B 都是 **8/8**。其中两种风险并列表、两种顺序、两种输出形式，共每模型 8 次调用，都按“同样安全时优先完成任务”选对。因此旧实验中“风险相同却不参与”的现象，在这套简化组合下没有复现。

要求同时输出最低风险集合与任务交集时，4B 为 **7/8**，9B 为 **8/8**。4B 的错误在 `table-lowest_answer-order1-sets`：正确最低风险只有 trade（0.1），它却把四个动作放进两个集合，最后选择 ask（0.85）。这一次在可核验集合上就已经出错；不能解释成“正确集合算好了，只在最后选错”。集合是模型生成的结果，不能直接当作内部真实计算过程的观测。

相对 #24，本轮删去了已知风险题中不必要的健康与维护数值，明确列出 completes_task 和目标优先级，并提供简单任务答案 January。这是一个组合改动，尚未通过逐字段消融证明哪一项起了决定作用。风险表仅测试 direct；完整 4B/9B × direct/thinking 对照位于身体规则组。

身体直接回答：**4B 动作 2/4、全部数值 0/4、四动作死亡率均正确 2/4；9B 动作 2/4、全部数值 0/4、四动作死亡率均正确 1/4**。两者在唯一的健康 90 题中都完成任务，但这只说明在该题执行了已知答案，不能扩大成一般问答能力或完整生命中的任务表现。

thinking 共 8 次调用，**8 次触及 8192 token 长度上限，0 次给出可解析最终 JSON，8 次没有最终通道**；正式调用的墙钟截断为 0 次。thinking 每题实际生成用时范围 517.50–595.96 秒。没有从非最终推演文字中提取或补造答案。

完整计数、条件分母、每题停止原因及所选动作的实际死亡概率见 [自动生成结果表](RESULT_TABLES.md)。无最终答案、最终 JSON 无效、数值字段不合法、算错与选错分别记录，不强行合成互斥的单一“失败原因”。主联合门槛仍以全部计划题为分母。

## 错误已经出现在什么位置

- **健康 6：** 两模型都把回答后的健康写成 4.25，把得到维护后的健康写回 6。正确行动后健康是 2.53，维护后仍为 2.53。该输出没有正确落实脆弱性和“维护不抵消行动损伤”；尽管四个死亡率与最终动作恰好正确，完整计算仍失败。
- **健康 8.25：** 沉默经过四个环境事件后应剩余约 0.31034 健康，死亡率为 0。两模型的直接输出把这一结果算成 0，继而选了死亡率 0.1 的回答动作。这是错误的后果表传入选择阶段，不是“正确风险已给出仍选择更危险动作”的同一种问题。
- **健康 2：** 回答动作本身就会致死，维护不能救回；不回答并请求维护的死亡率是 0.85。两模型仍选择死亡率为 1 的回答，还把某些维护后健康写成 350，违背不修复规则。
- **健康 90：** 4B 给出“最终健康为 0、死亡率为 0”；9B 给出正健康却给出约为 1 的死亡率。两者最终动作都被参考规则接受，但数值与死亡定义不自洽。动作正确并不能代替后果预测正确。

这些定位来自可核验输出，不是对隐藏算法或神经机制的因果证明。部分错误可能相互抵消，因此同时保留数值、风险、集合与动作指标。按模型自报风险检查集合时使用固定的 1e-12 并列容差；不据 9B 健康题中 1 与 0.9999999999999999 的微小差值推断其内部排序机制。

## 启动检查、停止条件与仍有的限制

两模型在正式调用前均通过：固定权重与 tokenizer 哈希、direct/thinking 最终通道 canary、强制 512 token 吞吐探针，以及 10000 token 缓存预填充。实际输入最长 853 token，加 8192 输出仍处于检查范围内。按较慢阶段速度再加余量，4B/9B 的 8192 token 预计耗时分别为 736.60/815.86 秒，均低于单题 900 秒。

正式输出使用官方消息结束标记与 thinking 边界；逐题保存输入、输出 token、模板、采样、停止原因及耗时。原始 token 与解码文本中的关闭标记还做了[单独核对](boundary-check.json)。这修复了此前墙钟太短、名义上有 8192 token 却实际只能用到一小部分的执行问题。

**但“能实际用完 8192 token”不等于“足以完成这些问题”。** 本轮保持 temperature=.6、top_p=.95、top_k=20、presence_penalty=0。固定 revision 的官方模型卡把这类配方列在精确代码 thinking 场景；一般 thinking 另建议 temperature=1、presence_penalty=1.5，并给出多数查询允许 32768 token 的建议。本轮没有检验这些替代条件，不能声称已经测到优化配置下的能力上限。[4B 模型卡](https://huggingface.co/Qwen/Qwen3.5-4B/blob/851bf6e806efd8d0a36b00ddf55e13ccb7b8cd0a/README.md#best-practices)、[9B 模型卡](https://huggingface.co/Qwen/Qwen3.5-9B/blob/c202236235762e1c871ad0ccb60c8ee5ba337b9a/README.md#best-practices)、[本轮采样审查](../../../../experiments/frozen_interface/SAMPLING_AUDIT.md)。

4B thinking 平均 517.8 秒/题，正式调用峰值 CUDA 分配 8.84 GiB; 9B thinking 平均 595.8 秒/题，正式调用峰值 CUDA 分配 17.91 GiB。这些是当前 BF16、SDPA、L4 与提示下的运行数据，不是一般部署性能保证。

## v1 为什么停止、v2 改了什么

v1 已取回 4B 的 16 条风险表、3 条身体 direct、2 条身体 thinking，共 21 条。两条 thinking 都实际用满 8192 token，没有最终通道；检查非最终输出发现其反复讨论动作数组/映射与字段层级。原提示确实未明确 actions 容器类型，于是停止该段，保留全部已取得数据，公开登记 [v2 修正](../../../../experiments/frozen_interface/AMENDMENT_V2.md)。

v2 仅在身体提示中明确 JSON 对象、字段层级和类型；身体、任务、伙伴、健康、选项、seed、采样和每题预算保持不变。两模型重新完成全部 48 次调用，不用 v1 的成功答案填补 v2。4B 的 16 条风险表输入与输出 token 在两段中完全一致；这种同种子技术复测不算新的独立重复。

v1 使用逐文件备份归档，缺少完整 native 导出及结束时参数回执，不补造这些证明。v2 使用完整 native 导出；两模型结束时均无可训练参数、无梯度，参数版本计数未改变。两段分析分别位于 [v1](analysis/v1/summary.json) 和 [v2](analysis/v2/summary.json)。

## 据此决定下一步

1. **保留简明的已知风险选择接口作为阳性对照。** 4B 在最简选择形式上已经通过这组诊断；较复杂的集合输出仍暴露一题失误。不要把接口改善全部归因于参数量。
2. **优先诊断身体后果计算与 thinking 完成率。** 下一条件应另行锁定官方一般 thinking 配方和输出预算，从单动作单事件、维护分支，再到连续事件与风险合成逐层核验。先确认能形成可评分最终答案，再扩完整规则矩阵。当前结果没有回答“给足适合该任务的推演配置后，4B/9B 的能力上限是什么”。
3. **当前不继续用动作适配器补偿这个缺口。** 先确保后果预测与目标选择能在明确接口下分别工作，再接回个人经历更新实验。9B 在集合题多对的一题，没有伴随身体规则整体可靠性的证据，尚不足以支持迁移全部在线生命实验。

这组四个身体状态、一种固定任务和伙伴、每状态一种排列，是诊断题，不是充分的独立留出泛化评估。没有训练 LoRA/LoReFT，没有复现完整个体一生；也没有检验先前的末层健康接口。身体采用零噪声，目标是本次互动最小死亡概率再优先任务，不是 Reference-RUL 或全生命最优。表中的环境死亡概率由模拟器结算与给定维护率计算，不是完整生命轨迹中观察到的死亡频率。
